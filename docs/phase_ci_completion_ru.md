# CI — автоматические тесты на GitHub: отчёт

## Итог

- При каждом push в `main`, где менялся код (`new_annotator/**`) или сам workflow, GitHub Actions запускает **все 15 наборов тестов** на четырёх машинах: **Windows и Ubuntu × Python 3.12 и 3.13**. Один прогон занимает около минуты, почти всё время уходит на установку зависимостей.
- Результат виден:
  - на вкладке **Actions** репозитория;
  - значком **Tests passing / failing** в начале README;
  - галочкой ✓ или крестиком ✗ у коммита на GitHub.
- В каждом прогоне есть таблица по наборам (Summary). Если что-то упало, GitHub пришлёт письмо.
- `new_annotator/run_tests.py` — тот же запуск локально (около 7 секунд):

  ```
  cd new_annotator
  .venv\Scripts\python run_tests.py              # все наборы
  .venv\Scripts\python run_tests.py review sam   # только те, в имени которых есть слово
  .venv\Scripts\python run_tests.py -v           # с полным выводом каждого набора
  ```

## Что CI нашёл сразу (и что исправлено)

1. **Установщик пускал Python 3.10 и 3.11, но закреплённая `numpy==2.5.3` требует 3.12+.**
   - На 3.10 или 3.11 `setup_venv.bat` упал бы на установке numpy.
   - Исправлено: `Deploy/setup_venv.bat` ищет 3.13 / 3.12 и проверяет `>= 3.12`. В `Deploy/README.md` и `README.md` теперь «Python 3.12+».
   - Заметки к релизам 1.7–1.8 на GitHub всё ещё говорят «3.10+». Поправить в следующем релизе.
2. **Тесты случайно падали при выходе** (access violation, код 139, «0 failed» в выводе), примерно в 30–80 % запусков у шести наборов с главным окном.
   - Причина: главное окно ставит фильтр клавиш на всё приложение (`installEventFilter`, для цифр — выбора класса). Окно, оставленное открытым, уничтожается при завершении Python, и Qt вызывает его `eventFilter` у полуразрушенного объекта.
   - Сама программа при обычном закрытии не падала (проверено 10 из 10 запусков).
   - Исправлено:
     - `closeEvent` снимает фильтр;
     - тесты с окном в конце закрывают все окна.
   - Результат: 0 падений из 48 запусков.

   Раньше это пропускалось, потому что смотрели на текст «passed», а не на код выхода. Именно такие вещи CI и ловит.

## Как устроено

`.github/workflows/tests.yml`:

| Часть | Что делает |
|---|---|
| `on: push / pull_request` + `paths` | когда запускать: push в `main` и pull request, только если менялся код или workflow (правка документации тесты не гоняет) |
| `workflow_dispatch` | кнопка **Run workflow** на вкладке Actions — запустить вручную |
| `concurrency` | новый push отменяет ещё идущий прогон той же ветки |
| `strategy.matrix` | 2 ОС × 2 версии Python = 4 задания параллельно; `fail-fast: false` — падение на одной ОС не прерывает другие |
| `actions/checkout@v7` | скачать репозиторий |
| `actions/setup-python@v7` + `cache: pip` | поставить Python; скачанные пакеты кэшируются по `requirements.txt` |
| `apt-get install libegl1 …` | на голой Ubuntu Qt не хватает системных библиотек даже без экрана |
| `run_tests.py` | каждый `test_*.py` в отдельном процессе, `QT_QPA_PLATFORM=offscreen`, UTF-8; код выхода 1, если хоть один набор упал; таблица — в `$GITHUB_STEP_SUMMARY` |

Ubuntu закреплена на `ubuntu-24.04`: список apt-пакетов зависит от версии системы, а `ubuntu-latest` с 19.10.2026 переходит на Ubuntu 26.

**Не проверяется в CI:**
- тесты с реальными моделями — нет видеокарты и моделей, они пропускаются сами без `ML_TEST_*`;
- установка из `Deploy` (`setup_venv.bat`);
- запуск с экраном.

## Риски и ограничения

- Linux проверяется только тестами. Скриптов `setup_venv.sh` / `run.sh` пока нет, запуск «из исходников» — вручную через `python -m venv`.
- Бесплатные минуты GitHub Actions для публичного репозитория не ограничены. Для приватного было бы 2000 минут в месяц, Windows считается ×2.
- Если поменять закреплённые версии в `requirements.txt`, CI сразу покажет, ставятся ли они на 3.12 и 3.13.
